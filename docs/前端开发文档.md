## 核心规范

### 1. ID 类型约束（最高优先级）

```typescript
// ✅ 正确 - 所有 ID 使用 string | null
interface Product {
  id: string
  shopId: string | null
}

// ❌ 错误 - 禁止使用 number
interface Product {
  id: number
}
```

**原因**: JS `Number.MAX_SAFE_INTEGER = 2^53-1`，雪花 ID 是 64 位，转 Number 会精度丢失

**禁止**:
- `Number(id)`, `parseInt(id)`, `+id`
- `id as number`
- `const numId = +id`

### 2. API 请求封装

```typescript
// api/request.ts - axios 实例
const request = axios.create({
  baseURL: '/api',
  timeout: 15000,
})

// 响应拦截器统一处理：
// - code !== 200 视为失败，reject 并提示
// - 401/1005 自动跳转登录页
```

### 3. API 返回格式

```typescript
// 统一返回格式
interface ApiResult<T> {
  code: number
  message: string
  data: T
}

// 分页返回
interface PageResult<T> {
  list: T[]
  total: number
  page: number
  pageSize: number
}
```

### 4. 错误码协议

```typescript
// 前端根据 code 处理业务逻辑
switch (code) {
  case 200:   // 成功
  case 1005:  // Token 无效 → 跳转登录
  case 1003:  // 用户不存在 → 跳转登录
  case 2006:  // 积分不足
  case 2004:  // 商品下架
  // ...
}
```

## 页面与路由

### 布局与角色

| 路径 | 布局 | 角色 | 说明 |
|------|------|------|------|
| `/login` | auth | - | 登录页 |

| `/admin/*` | AdminLayout | 1 | 管理员 |
| `/operator/*` | OperatorLayout | 2 | 店铺用户 |
| `/user/*` | UserLayout | 3 | 普通用户 |

### 路由守卫

- `router/guards.ts` 实现路由拦截
- 根据用户角色自动跳转对应角色首页
- 未登录自动跳转登录页

## 组件规范

### 命名规范

- 组件文件: PascalCase (如 `ProductCard.vue`)
- 组件引用: kebab-case (如 `<ProductCard />`)
- 组合式函数: camelCase 以 `use` 开头 (如 `useUserAuth.ts`)

### API 错误处理模式

```typescript
// 推荐：在 API 层统一处理错误
async function fetchProducts(params: PageRequest) {
  try {
    return await request.get<Result<PageResult<Product>>>('/operator/products', { params })
  } catch (error) {
    // 错误已在拦截器处理
    throw error
  }
}

// 业务层直接使用
const products = await fetchProducts({ page: 1, size: 10 })
```

## AI 自检清单

开发或修改代码后，按以下清单自检：

### 文件检查

- [ ] `types/api.ts` 中是否已添加新类型
- [ ] API 文件是否已导出新接口
- [ ] 路由是否添加页面组件

### 类型检查

- [ ] 所有 ID 类型是否为 `string`（禁止 `number`）
- [ ] 枚举类型是否使用后端定义的值
- [ ] 可选字段是否使用 `| null` 或 `?`

### API 检查

- [ ] 请求参数是否匹配后端 DTO
- [ ] 响应数据是否正确解析
- [ ] 错误码是否有对应处理

### 安全检查

- [ ] 禁止 `v-html`（XSS 风险）
- [ ] 敏感数据是否需要脱敏处理

### 代码质量

- [ ] 是否有 `console.log` 调试代码
- [ ] 重复代码是否抽取为复用函数
- [ ] 组件是否遵循单一职责原则

## AI 开发流程

### 1. 新增功能

1. 确认功能对应的角色和 API 前缀
2. 在 `types/api.ts` 添加类型定义
3. 在对应 `api/` 文件添加接口
4. 创建或复用页面组件
5. 在 `router/index.ts` 添加路由
6. 运行 `pnpm type-check` 验证类型
7. 运行 `pnpm lint` 检查代码规范

### 2. 修改现有功能

1. 确认修改范围（前端/后端/两端）
2. 同步修改 `types/api.ts` 类型定义
3. 更新对应的 API 接口
4. 更新页面组件
5. 自检清单验证

### 3. 自检脚本（可保存为 checklist.md）

```
前端自检清单:
□ ID 类型正确 (string)
□ API 类型已导出
□ 路由已配置
□ ESLint 无 error
□ TypeScript 类型检查通过
□ 页面可正常渲染
□ 功能流程测试通过
```

|------|------|
